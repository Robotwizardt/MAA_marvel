# MAA Marvel 公共战斗引擎与征服模式设计

## 1. 背景与目标

MAA_marvel 是面向国服《漫威终极逆转》的 MaaFramework 项目。项目参考
[booster-bot](https://github.com/little-fort/booster-bot) 的状态机思路，在不复制其
C# 代码与图片资源的前提下，重新实现适用于国服安卓端的自动对战流程。

最终产品覆盖征服、天梯和限时活动三种模式。为了让每个阶段都能独立运行、测试
和验收，开发顺序固定为：

1. 公共战斗引擎与征服模式；
2. 天梯模式与可配置回合撤退；
3. 限时活动模式；
4. 跨模式长期挂机和整体联调。

本文只定义第一阶段。第一阶段的目标是在 `720×1280` 国服安卓画面上，通过 ADB
安全地完成征服模式导航、档位选择、匹配、自动对战、撤退、结算、停止条件和异常
恢复，同时为后续模式提供可复用的公共战斗引擎。

## 2. 已确认的运行环境

- 控制端：MaaFramework ADB Controller；
- 首要运行环境：MuMu 12；
- 设备序列号不写入项目配置，由通用 UI 在运行时选择；
- 游戏包名：`com.netease.ms`；
- 标准画面：完整竖屏 `720×1280`，无黑边、刘海裁切或悬浮导航栏；
- 第一阶段只支持国服安卓端，不承诺 Win32 客户端兼容性。

实机探索已经确认主界面、游戏模式列表、征服入口、无限征服付费入口、试炼之地
免费入口及征服赛前页的基本布局。探索期间没有开始匹配、消耗门票或领取奖励。

## 3. 许可与来源边界

MAA_marvel 保持 MIT 许可证。booster-bot 仅作为行为和状态机设计参考：

- 不复制 booster-bot 的 C# 源码；
- 不复制 booster-bot 的模板图片；
- 所有流水线与 Python Agent 逻辑独立实现；
- 所有生产模板均从国服安卓端重新采集和裁剪；
- README 中注明参考来源和原项目链接。

## 4. 总体架构

系统采用 JSON 流水线与 Python Agent 混合架构。

### 4.1 任务界面层

`assets/interface.json` 和 `assets/tasks/` 定义用户可见任务和配置。第一阶段提供
“征服模式自动对战”任务。后续模式复用公共配置，但拥有各自的撤退和结算选项。

### 4.2 JSON 流水线层

流水线负责确定性的页面识别和操作：

- 启动并识别游戏；
- 从已知页面返回主界面；
- 进入游戏模式列表；
- 选择征服模式和档位；
- 校验免费入口或已有门票；
- 进入赛前页并开始匹配；
- 识别回合、等待、撤退、轮间和整场结算页面；
- 处理明确识别出的重连、继续、下一步和返回按钮；
- 通过 `StopApp` 与 `StartApp` 重启 `com.netease.ms`。

流水线不保存复杂会话状态，也不在未知画面上执行盲点。

### 4.3 Python Agent 层

Agent 负责需要状态、随机数或计算的行为：

- 随机出牌、阿加莎托管和实验 OCR 出牌；
- 对局数量与运行时间统计；
- SNAP、撤退和整场认输决策；
- 征服档位候选排序；
- 匹配、回合和未知状态超时；
- 恢复次数、游戏重启次数与停止原因。

### 4.4 国服资源层

模板只截取稳定局部特征。玩家头像、昵称、卡组、活动轮播、货币数值、任务内容
和动态倒计时不进入关键模板。关键点击必须由当次识别结果或经过安全校验的固定
ROI 驱动。

## 5. 代码和资源边界

第一阶段采用以下职责划分：

- `assets/interface.json`：项目元信息、ADB 控制器、Agent 启动方式和公共选项；
- `assets/tasks/`：用户可见任务；
- `assets/resource/pipeline/common/`：启动、主界面、公共战斗和结算节点；
- `assets/resource/pipeline/conquest/`：征服入口、档位、门票、赛前、轮间和整场结算；
- `assets/resource/pipeline/recovery/`：重连、返回、重启和失败终止；
- `assets/resource/image/common/`：公共页面局部模板；
- `assets/resource/image/conquest/`：征服页面局部模板；
- `agent/strategies/`：三种互相独立的出牌策略；
- `agent/session/`：任务配置、计数器、计时器和恢复状态；
- `agent/actions/`：由流水线调用的自定义动作；
- `tests/`：Agent 单元测试、配置检查和截图回归样例。

模板示例 `agent/my_action.py` 与 `agent/my_reco.py` 删除。现有
`agent/chose_cards_reco.py` 重构为实验 OCR 策略。已有征服入口坐标可作为实机探索
线索，但必须经过新截图验证后才能进入生产流水线。

## 6. 第一阶段任务配置

“征服模式自动对战”提供以下选项：

| 配置 | 取值与默认值 |
| --- | --- |
| 出牌策略 | 随机出牌 / 阿加莎托管 / OCR 选牌（实验）；默认随机出牌 |
| 最高征服档位 | 试炼之地 / 白银 / 黄金 / 无限；默认试炼之地 |
| 无票行为 | 回退试炼之地 / 停止任务；默认回退试炼之地 |
| 自动撤退 | 关闭或完成第 1–6 回合后撤退；默认关闭 |
| 撤退后 | 继续下一轮 / 认输整场；默认继续下一轮 |
| SNAP | 关闭 / 固定概率 / 每局必定执行；默认关闭 |
| SNAP 概率 | `0`–`100`，仅固定概率模式生效；默认 `46` |
| 最大对局数 | 非负整数，`0` 表示不限制；默认 `0` |
| 最大运行分钟数 | 非负整数，`0` 表示不限制；默认 `0` |
| 匹配超时 | 正整数秒；默认 `600` |
| 自动重启游戏 | 开启 / 关闭；默认开启 |

如果最大对局数和最大运行分钟数均为 `0`，任务持续运行直至用户停止或安全恢复
达到上限。配置“完成第 3 回合后撤退”时，脚本完成第 3 回合，并在第 4 回合开始
时执行撤退。

## 7. 公共战斗引擎

### 7.1 战斗状态

战斗引擎组合识别以下稳定区域：

- 可点击的结束回合按钮；
- 已结束操作、正在等待对手的状态；
- 撤退入口；
- 轮间继续或整场结算入口。

单一模板不决定完整战斗状态。引擎将多个局部识别结果组合为“可操作、等待、轮间、
整场结束、未知”之一。

### 7.2 随机出牌

随机策略将最多四个手牌槽位随机排序，依次拖向三个随机区域。每次拖动后检查零
能量状态；识别到零能量即提前停止。完成一轮后若仍有能量，可再尝试一轮。拖动
起点、终点和点击点加入小范围随机偏移，但始终限制在已验证的手牌和区域 ROI 内。

### 7.3 阿加莎托管

阿加莎策略不拖动卡牌。引擎等待游戏完成自动出牌，在结束回合按钮可用时点击结束
回合。超时或页面转入结算时立即停止等待并重新识别状态。

### 7.4 OCR 选牌（实验）

实验策略识别当前能量和各手牌费用，选择费用最高且可支付的卡牌，并在能量允许时
重复执行。识别结果缺失、冲突或置信度不足时停止出牌并结束回合，不自动回退到随机
策略。日志记录能量、候选卡牌、选择结果和失败原因。该策略不作为第一阶段验收门槛。

### 7.5 回合顺序

每回合按以下顺序执行：

1. 等待结束回合按钮进入可操作状态；
2. 根据已选策略执行出牌；
3. 根据当前模式的 SNAP 配置决定是否 SNAP；
4. 点击结束回合；
5. 等待对手并识别新回合、撤退条件、轮间或整场结算；
6. 超时后进入统一恢复流程。

## 8. 征服模式状态流

### 8.1 导航和档位选择

1. 从任意已知页面回到主界面；
2. 进入游戏模式列表，滚动并识别“征服模式”；
3. 进入征服大厅，将档位轮播重置到可确认的位置；
4. 从用户允许的最高档位向低档位检查门票；
5. 选择第一个具有门票的允许档位；
6. 如果没有门票，则按配置回退免费试炼之地或停止任务。

档位顺序固定为试炼之地、白银、黄金、无限。选择逻辑以档位语义为依据，不比较
枚举的偶然数值大小。

### 8.2 付费保护

只允许点击两类入口：

- 试炼之地明确识别出的免费“进入”按钮；
- 同时识别出已有门票和正确档位的入口。

如果页面显示金块图标、金块数值、付费确认或入口识别不确定，本轮选择立即失败并
返回档位选择。任何恢复流程都不得点击入场按钮所在区域。

### 8.3 赛前和匹配

赛前页只点击中央“开战”按钮的识别框，避开左侧“删除”和右侧商店。匹配超过默认
600 秒后取消并重新进入；连续失败转入统一恢复流程。

### 8.4 轮间和整场结算

每轮调用公共战斗引擎。达到撤退条件时：

- “继续下一轮”只完成当前轮撤退，并进入下一轮；
- “认输整场”在撤退后识别并确认认输，然后进入整场结算。

整场结束后，只处理明确识别出的下一步、继续和门票领取页面，直到重新识别征服
大厅。随后更新对局数、运行时间和门票状态，并决定继续或停止。

## 9. 异常恢复与安全策略

恢复严格按以下顺序进行：

1. 同一状态间隔截图重试 3 次；
2. 处理明确识别出的重连、继续、下一步或返回按钮；
3. 发送一次安卓返回键后重新识别，最多逐级返回 3 次；
4. 未知状态持续 120 秒，或匹配、战斗超过对应超时后，按配置重启游戏；
5. 使用 MaaFramework `StopApp` 和 `StartApp` 操作重启 `com.netease.ms`；
6. 等待主界面加载并从当前任务入口重新导航；
7. 单次任务最多自动重启 3 次，仍失败则安全停止。

安全约束：

- 未识别到目标按钮时不使用固定坐标盲点；
- 付费入口或付费弹窗识别不确定时停止当前路径；
- 动态轮播和货币数字不作为关键状态条件；
- 未知状态保存最后截图并记录节点、置信度、耗时、重试和恢复动作；
- 弹窗必须使用对应局部模板识别，不使用全屏 OCR 搜索字符 `X`；
- Agent、流水线或控制器报告停止后，不再发布新的点击或拖动动作。

## 10. 数据流与停止语义

任务开始时，界面配置转换为一次不可变的会话配置。Agent 维护以下运行状态：

- 任务开始时间；
- 已完成整场征服数量；
- 当前征服档位；
- 当前回合号；
- 本局是否已 SNAP；
- 连续未知状态次数；
- 自动重启次数；
- 最后成功识别状态；
- 最终停止原因。

游戏重启不重置会话计数。用户主动停止、最大对局数、最大运行时间、安全恢复上限
和无票停止策略均可结束任务。任务结束必须给出明确原因。

## 11. 测试策略

### 11.1 单元测试

遵循测试驱动开发，先为以下纯逻辑写失败测试：

- 征服档位候选排序和无票回退；
- 金块付费入口拒绝规则；
- 对局数和运行时间停止条件；
- 完成指定回合后的撤退时机；
- SNAP 关闭、固定概率和必定执行；
- 未知状态重试、返回、重启和最终停止；
- 随机、阿加莎和 OCR 策略的动作决策。

### 11.2 配置和 schema 验证

所有接口、任务、流水线、自定义识别和自定义动作参数必须通过仓库自带 schema
检查。格式化结果不得改变节点语义。

### 11.3 离线截图回归

每个关键状态保存正样本和相似负样本，至少覆盖：

- 主界面与动态轮播变体；
- 游戏模式列表；
- 征服四个档位；
- 免费、门票和金块付费入口；
- 赛前、匹配、可操作回合和等待状态；
- 撤退、轮间、整场结算和门票领取；
- 重连和常见弹窗。

当前 `.tmp` 中的探索截图只用于设计分析。生产模板必须重新裁剪并配套标注用途、
ROI 和阈值。

### 11.4 ADB 实机验收

实机测试按风险递增：

1. 只导航到试炼之地赛前页；
2. 完成一次随机出牌对局；
3. 完成一次阿加莎托管对局；
4. 验证撤退与整场认输；
5. 切回桌面并验证返回游戏；
6. 停止游戏进程并验证自动重启；
7. 进行至少 60 分钟连续运行测试。

涉及开始匹配、撤退、认输、奖励领取或停止游戏进程的首次实机测试，执行前需得到
用户明确授权。

## 12. 第一阶段验收标准

第一阶段在满足以下条件后完成：

- 从主界面、模式页、征服大厅或赛前页启动均能进入正确流程；
- 不点击任何金块付费入口；
- 随机出牌和阿加莎托管均能完成对局与结算；
- SNAP、回合撤退、整场认输、对局数和时间停止条件生效；
- 未知状态能够按设计逐级恢复；
- 游戏能够通过 MaaFramework 动作自动重启并继续会话；
- 所有单元测试、schema 检查和离线截图回归通过；
- 完成至少 60 分钟连续运行验收；
- OCR 实验模式能输出可诊断结果，但其准确率不阻塞第一阶段完成。

## 13. 第一阶段不包含的内容

- 天梯模式完整流水线；
- 限时活动模式完整流水线；
- Win32 客户端支持；
- 基于卡牌效果、区域效果或胜负预测的智能决策；
- 自动购买门票、金币或任何付费资源；
- 复制或兼容 booster-bot 的旧版 Steam 模板。

后续阶段必须复用本文定义的公共战斗、会话、恢复和安全接口，不能为单个模式复制
一套独立实现。
